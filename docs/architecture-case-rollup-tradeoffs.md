# 实战场景：海量数据下的多级报表与动态时区上卷 (Roll-up)

## 业务背景与挑战
在真实的全球化金融/交易业务中，往往面临以下极限需求：
1. **海量写入与留存**：每日摄入 3 亿笔交易数据，并且需要长达 6 个月的明细查询能力（共计约 540 亿条历史数据）。
2. **多时区动态报表**：需要支持跨时区的及时聚合。
3. **多粒度级联报表**：财务端需要基于特定的固定时区，产出精确的日报表、周报表、月报表。

## 业界顶尖公司的解决方案 (2023-2026)
根据最近三年（2023-2026）的业界公开技术分享，处理此类 ClickHouse 海量去重与预计算挑战的顶尖团队（如 PostHog, Cloudflare, Uber）和核心维护商（Altinity）通常采用以下成熟方案：

1. **PostHog (数百亿级实时事件分析)**：
   * 在早期的技术演进中，PostHog 彻底放弃了依赖 Kafka/Flink 做 Exactly-Once 的强一致性摄入。他们转而拥抱 ClickHouse Native 的方案：将含有重复数据的流直接打入 `ReplacingMergeTree`，然后利用 Materialized View (物化视图) 实时将新数据块提取到 `AggregatingMergeTree`。
   * 结论：利用 ClickHouse 引擎的异步合并去处理重复，极大降低了摄入层的架构脆弱性。
2. **Cloudflare (万亿级 HTTP 流量观测)**：
   * Cloudflare 每天处理极其恐怖的日志量，他们在博客中指出，应对这种规模的唯一解法是 **Base-Time-Bucket (基础时间桶) 预计算**。他们不会为“1小时”、“1天”、“1周”分别建表，而是统一聚合到较小的时间粒度（如 1 分钟或 10 分钟），上层所有的长周期查询全部通过动态聚合产生。
3. **Altinity (ClickHouse 核心服务商)**：
   * Altinity 2024 年的最佳实践明确指出：虽然现代 ClickHouse 的 `FINAL` 查询性能通过多线程得到了史诗级加强（可用于日常查明细），但对于高频 Dashboard 报表，强依赖 `ReplacingMergeTree + FINAL` 依然会消耗大量 CPU。**“物化视图 + 聚合树 (AggregatingMergeTree)”** 才是高并发报表的最终解法。

## 方案对比与 Trade-off 分析

针对您的“明细 -> 半小时 -> 日/周/月”需求，业界有三种主流实现路线。相较之下，**当前 Repo 推荐的“基础时间桶动态上卷”是最具性价比和灵活度的方案。**

### 方案 A：传统级联物化视图 (Cascading MVs)
* **架构**：`明细表` -> MV1 -> `半小时表` -> MV2 -> `日表` -> MV3 -> `月表`。
* **优点 (Pros)**：对于“月报表”的查询，底层真正做到了极度预计算，查询耗时趋近于 0，哪怕查询 10 年的数据也是瞬间返回。
* **缺点 (Cons)**：
  * **写放大 (Write Amplification)**：每一层都会产生独立的物理存储和 Zookeeper 元数据，严重消耗 8C32G 节点的 IO/内存。
  * **时区锁死 (Timezone Lock-in)**：一旦在写入“日表”时按 UTC+8 做了切分，日后财务要求按 UTC+0 看日报表时，这张日表就彻底废了，必须重算历史数据。

### 方案 B：外部流式预计算 (Flink + ClickHouse)
* **架构**：Kafka -> Flink (窗口计算半小时/日/月指标) -> ClickHouse 仅作为 KV 结果库。
* **优点 (Pros)**：ClickHouse 毫无计算压力，完全交由 Flink 扛下并发，且能在 Flink 层做到严格的 Exactly-Once 状态保证。
* **缺点 (Cons)**：
  * **运维成本极高**：引入了沉重的 JVM 生态和 Flink 状态后端。
  * **容错恢复难**：如果是长达一个月的窗口，Flink 状态一旦丢失，重算半年数据的代价极大。

### 方案 C：Base-Time-Bucket 动态上卷 (当前 Repo 最佳实践) 🌟
* **架构**：`明细表 (ReplacingMergeTree, 保留半年)` -> 单个 MV -> `半小时基表 (AggregatingMergeTree, 保留数年)`。所有日、周、月报表均通过 SQL 在查询半小时基表时按需动态上卷。
* **优点 (Pros)**：
  * **终极时区灵活度**：由于底层粒度是半小时，业务可以在 `SELECT` 查询时动态传入 `toStartOfDay(time, 'Asia/Tokyo')`，完美规避时区和夏令时问题。
  * **极致护航 8C32G 节点**：没有写放大，节点后台只维护这一张较小的聚合表，Zookeeper 压力极小。
  * **查询极速**：半小时基表每天的数据行数通常不到 10 万行，半年仅 1000 多万行，ClickHouse 的 `sumMerge` 扫描千万行仅需 10~50 毫秒。
* **缺点 (Cons)**：相较于方案 A 存在微量的“读放大”（需要查询几千行半小时的中间态来合并成一个月），但在 ClickHouse 的向量化执行引擎面前，这种读放大的开销基本可以忽略不计。

## 最终落地指南结论
结合您的 Aiven 8C32G (3 节点) 资源配置：
1. **明细表**：每天 3 亿条，**按天分区**，保留 6 个月。直接使用 `ReplacingMergeTree`，利用 Kafka 攒大批次写入，完美胜任。
2. **唯一报表表**：通过单个物化视图产出“半小时粒度”的 `AggregatingMergeTree`，保留多年，解决所有的报表查询。
3. 此方案与当前业界顶尖数据团队（Cloudflare / PostHog）的核心思路完全吻合，兼顾了成本、性能与架构弹性。
