# 三类日常数据问题的排查顺序

顺序比工具重要。三类各有一条固定走法，走到底还查不出来才允许换思路。

三类里最难的是「少了」，因为它不报错。「多了」有明确特征（重复行长得一样、间隔成档），「不对」至少能看见数字不合理。「少了」往往在事故之后很久才发现。

## 多了：重复行

1. 先固定口径再数。同一个 `(id, version)` 对，换一列就换一套结论。
2. 数多余行，按小时切窗：

   ```sql
   SELECT count() AS rows, uniqExact(id, version) AS keys
   FROM events
   WHERE _partition_id = '20260730'
     AND settle_time >= {hour_start_ms}
     AND settle_time <  {hour_start_ms} + 3600000;
   ```

   `rows - keys` 是这一小时的多余行数。`_partition_id` 裁分区，排序键首列裁行，两层都要有，否则整分区扫。
3. 看重复组的写入时间间隔分布。间隔集中在少数几档，说明是同一类失败反复发生，样本数等于档数而不是行数。间隔是连续一片，另找原因。
4. 判每组的行数。都是 2 行，指向一轮失败；出现 3 行以上，中间那次要么没提交、要么被去重拦了，两种解释要能分开。
5. 排除上游双发。抽几组回查上游日志，写明抽了几组、覆盖多少比例，没抽到的部分别写成结论。
6. 定位幂等层哪一环失效。顺序是：客户端有没有重试循环、框架重投的是不是同一批、token 有没有带上、服务端窗口还在不在。前三环在 `mechanism-map.md` 的接入侧那张表里都有行号。
7. 窗口这条在 lab 里是实验 02（lab 实测）。它同时给出一个修正：块数超窗和旧块真被清掉之间隔着一个裁剪周期（偏差 A），算窗口的时候按 30 加 10 秒量级留余量。注意这个 30 到 40 秒是在一张一直有写入的表上量到的；`max_cleanup_delay_period` 是 300 秒，空闲的表上裁剪周期会不会退到那个量级，这个 lab 没量过（待一手观察）。**不是没想测，是本地测不了**：表一空闲，`blocks/` 就不再变化，znode 数看不出裁剪线程醒了几次，得把服务端日志级别调到 debug 去读 `ReplicatedMergeTreeCleanupThread` 的睡眠时长——那要改配置重启，超出这个 lab「起完就能跑」的边界。要拿这条线做决策，先自己测一次。

## 少了：数据没进来

按这个顺序往下走，每一步都能二分。

1. 上游到底产出多少。先确认不是上游自己少写了，这一步不花 ClickHouse 资源。
2. Kafka 侧该时间段的量。上游与 topic 对不上，问题在 producer 或 broker，与 ClickHouse 无关。
3. connector 有没有失败批次。看 task 状态与重启次数，再看 DLQ topic 有没有量。`errors.tolerance` 默认 `none`、DLQ topic 默认空（已核，Confluent 托管 connector 页），意思是坏消息默认让 task 失败，不会静悄悄进 DLQ。反过来说，一旦有人配了 DLQ，被吞掉的批次只在那个 topic 里找得到。
4. offset 断点。committed 与 log-end 的差是积压，committed 长时间不动是卡住。
5. INSERT 有没有真的执行、写进行数多少。`system.query_log` 里查这条 INSERT 的 `written_rows`，与批次大小对比。写了但行数少，看是不是格式或类型转换按批截断。
6. 落错分区。按事件时间查不到，用 `_partition_id` 反查它到底落在哪个分区。这一条经常和时区有关，见下面第三节。

待建实验 09：造一个坏批次（列缺失、类型不合），分别在 `errors.tolerance` 为 `none` 和配了 DLQ 两种设置下看数据去哪了。默认值已核，吞数据的具体形状还没有一手记录（待一手观察）。

## 不对：数字对不上

前三步各能砍掉一大半可能。

1. 两边比的是不是同一条时间轴。事件时间还是写入时间，分区键 `toYYYYMMDD(settle_time)` 按哪个时区截断。**同一批数据在两种时区声明下确实会落到不同分区**（lab 实测，实验 10）：同一个绝对时刻 `2026-07-30 23:30:00 UTC`，列声明成 `DateTime('UTC')` 落在 `20260730`，声明成 `DateTime('Asia/Shanghai')` 落在 `20260731`。两张表行数一样、分区键表达式一样、都不报错，但按事件日 `20260730` 查，一张给 2 行、另一张只给 1 行。这就是「少了一行」最常见的形状。生产上是不是真踩过这一条，仍然没有一手记录（待一手观察）。
2. JOIN 有没有放大行数。先把右表的键单独数一遍唯一性。放大是 INNER JOIN 在右表重复键上的正常行为：右表每个键 2 行时，3 行左表 `INNER`／`LEFT JOIN` 出来都是 6 行，`ANY INNER`／`ANY LEFT` 都是 3 行（lab 实测，实验 10）。`ANY JOIN` 具体留下哪一行，这条查清楚了：官方 JOIN 语句页**根本没有承诺**是哪一行（已核，2026-09-17；该页只给了 `ANY` 的语法和 `join_any_take_last_row` 这个设置），而这个设置会直接翻转结果——实测默认 `0` 取右表先出现的那行，设成 `1` 取后出现的那行（lab 实测，实验 10）。所以「`ANY JOIN` 取第一行」不是它的性质，连默认行为都是可配的，任何文档都别这么写。要确定性就自己 `LIMIT 1 BY` 加排序列。
3. 聚合口径。`uniqExact` 是精确的，`uniq` 是近似值，报表里两套混用过就查不干净。25.3 上量到的误差（lab 实测，实验 10）：

   | 基数 | `uniq` | 误差 |
   |---|---|---|
   | 10 万 | 100315 | +0.315% |
   | 100 万 | 1001943 | +0.194% |
   | 1000 万 | 9983940 | −0.161% |

   注意误差**两个方向都有**，不是单调偏大，所以不能靠固定系数修正回去。对账场景一律 `uniqExact`。另外三个常见项：`Nullable` 列进聚合、整数除法截断、`UInt64` 求和溢出。
4. 读 `ReplacingMergeTree` 有没有带 `FINAL`。不带就是可能读到多份，去重发生在后台合并时，时间不由你定。`FINAL` 的代价是每次查询现场合并，是一笔长期开销，别拿它当默认读法。
5. 上面全部排完仍然不对，才去查设置差异和版本差异。

## 对账口径模板

一套口径写成三行，贴在跑数的那个查询旁边，别只存在脑子里。

```sql
-- 键：(id, version)
-- 切窗：_partition_id 加 settle_time，小时粒度
-- 计数：count() - uniqExact(id, version)，精确口径，不用 uniq
```

三条约定：键要带版本列，只按 `id` 数会把正常的新版本算成重复；切窗用业务时间，用写入时间会把迟到行算到错误的窗口里；对账场景只用 `uniqExact`。
