# ClickHouse 核心表引擎原理与选型白皮书 (Engine Selection Guide)

在 ClickHouse 中，**表引擎（Table Engine）决定了数据的存储格式、去重逻辑、聚合方式以及高可用能力**。对于日均 3 亿笔交易（300M/day）的金融/交易级业务，选错引擎往往意味着灾难性的 I/O 放大或数据不一致。

本文档专门针对 **3 节点高可用架构（如 Aiven 托管集群）**，系统梳理了核心引擎的底层原理与业务选型标准。

---

## 🛡️ 一、 核心底座：`Replicated` 复制壳机制
在讨论具体的业务引擎之前，必须先理解在 3 节点集群上绝对绕不开的修饰符：`Replicated`。

* **原理本质**：`Replicated` 不是一种独立的业务逻辑，而是套在任何 `MergeTree` 家族引擎外部的**网络复制壳**。它依赖 ZooKeeper (或 ClickHouse Keeper) 来协调各个节点。
* **高可用表现**：当您写入数据到“节点 A”时，节点 A 只是落盘并向 Keeper 注册一条 Metadata。随后，节点 B 和节点 C 会监听到 Keeper 的变化，自动通过内部网络把数据块（Part）从节点 A 拉取到自己的本地硬盘。这就实现了 3 节点之间的强力容灾。
* **Aiven 托管环境的“潜规则”**：为了保证 3 节点的 SLA 承诺，Aiven 做了控制面拦截。即便您手滑写了 `ENGINE = MergeTree`，Aiven 也会在后台强行将其改写为 `ENGINE = ReplicatedMergeTree`。但在生产环境的 DDL 脚本中，**我们必须显式声明带有 `Replicated` 前缀的引擎名，以确保代码逻辑绝对严谨**。

---

## ⚙️ 二、 四大核心业务引擎剖析 (The MergeTree Family)

套上 `Replicated` 壳之后，内部的业务数据合并逻辑由以下四大核心引擎决定：

### 1. 基础合并树 (ReplicatedMergeTree)
* **核心机制**：ClickHouse 最基础、查询极快的引擎。数据纯粹**追加写入 (Append-Only)**，系统在后台将小文件块排序并合并成大文件块。
* **致命缺陷**：**不保证主键唯一，不自动去重**。即使两行数据的主键完全一样，它也会原样保存两份。
* **适用场景**：绝不变更的时序日志流，例如 Nginx 访问日志、传感器指标打点。

### 2. 替换合并树 (ReplicatedReplacingMergeTree) 🌟 [本项目明细层首选]
* **核心机制**：在基础合并树之上，增加了**“根据版本号去重”**的能力。如果后台合并时遇到了主键（`ORDER BY`）相同的多行数据，它会自动丢弃旧数据，只保留指定版本列（如 `create_time`）最大的那一行。结合查询时的 `FINAL` 关键字，能在读时实现 100% 强一致去重。
* **适用场景**：
  * **容忍 Kafka 重投**：架构无需配置脆弱的分布式事务锁。如果一条订单被重投了 10 遍，底层也会静默折叠成 1 遍。
  * **状态更新 (CDC)**：订单状态从“支付”变“发货”，直接重发一条带新时间戳的记录即可实现无痛 Update。

### 3. 聚合合并树 (ReplicatedAggregatingMergeTree) 🌟 [本项目报表层首选]
* **核心机制**：这是一种**“不存明细，只存中间状态”**的超级引擎。它会将拥有相同主键的数据，按照预先定义的聚合函数（如 `sumState`, `uniqState`）合并成高度压缩的二进制状态树。
* **适用场景**：**物化视图 (Materialized View) 的唯一最佳拍档**。
  针对每天 3 亿笔的海量交易，我们建立一张基于半小时维度的 `ReplicatedAggregatingMergeTree`，将千亿级明细降维坍缩成极小的中间状态表。查询时配合 `sumMerge()`，以毫秒级响应支撑全球动态时区日报、周报。

### 4. 折叠合并树 (ReplicatedCollapsingMergeTree)
* **核心机制**：要求每一行数据多带一个 `Sign` 字段（取值 1 或 -1）。写入 `Sign = -1` 被视为“撤销操作”。后台合并时，如果碰到主键相同且 Sign 互为正负的两行数据，它们会物理“湮灭”抵消。
* **适用场景**：**严谨的财务冲销系统**。如果一笔已完成的订单发生了退款，业务系统直接追加一条 `Sign = -1` 的复刻数据过去即可让流水抵消。

## 🎯 三、 当前项目的引擎架构映射

基于上述原理，我们当前项目的百万级/亿级吞吐量最佳实践，形成了如下坚不可摧的搭配：

| 架构分层 | 选型引擎 | 核心原因 |
| :--- | :--- | :--- |
| **ODS 明细层**<br/>(`events_raw`) | **ReplicatedReplacingMergeTree** | 依托 `Replicated` 实现 3 节点防宕机容灾；依托 `Replacing` 吸纳由于断网导致的 Kafka 消息重复重发，将不可变写化解为幂等更新。 |
| **DWS 报表层**<br/>(`report_mv`) | **ReplicatedAggregatingMergeTree** | 利用聚合状态树极大降低存储和 I/O 成本，同时完美支持由于网络延迟导致的“迟到数据”的精准历史累加。 |

通过对表引擎的精准控制，我们将海量数据的去重、容灾、聚合压力完美卸载到了 ClickHouse 的 C++ 底层 C-Core 合并机制上，从而保障了上层业务与运维的极致简单。
