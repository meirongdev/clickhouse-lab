## 4. 深度技术解析：从 8c32g 到 16c64g 的跨越

### 4.1 为什么 16c64g 对高基数 `count(DISTINCT id)` 产生质变？
在 ClickHouse 中，`SELECT count(DISTINCT id)` 采用基于哈希表的精确聚合算法：
1. **内存占用由基数决定**：3 亿个互不相同的 UUID 字符串在哈希表中的固定内存开销约为 **18.1 ~ 18.2 GiB**。
2. **在 4c16g 下**：内存上限仅 9.94 GiB，跑至 2.2 亿行直接触发 `Code: 241 MEMORY_LIMIT_EXCEEDED` 强杀中断。
3. **在 8c32g 下**：内存上限 21.52 GiB，18.11 GiB 虽能跑通，但**已消耗了单节点 84.2% 的可用内存配额**。一旦此时并发第二条查询，极易引发连锁 OOM。耗时为 17.15 秒。
4. **在 16c64g 下**：内存上限提升至 **43.14 GiB**。
   - 18.18 GiB 仅占单机内存上限的 **42.1%**，单机依然保留超过 **25 GiB** 的安全缓冲池；
   - 16 线程哈希并行聚合使得运算耗时直接从 17.15 秒**压缩到 6.71 秒（提速 2.56 倍）**！

### 4.2 计算密集型分析查询的线性加速
对于带有 `FINAL` 折叠的多指标聚合计算 (`sum`, `avg`, `min`, `max`) 和跳数索引过滤检索：
- 4c16g -> 8c32g -> 16c64g：
  - 多指标聚合：42.18s -> 10.85s -> **6.47s**（加速比 **6.52x**）；
  - 跳数索引过滤：16.71s -> 4.55s -> **2.63s**（加速比 **6.35x**）。
- 算力提升直接将分析师的交互式报表等待时间从「半分钟级（无法忍受）」压入「秒级响应（体验极佳）」。
